## ④ 如实说明

**走通部分**：输入核查与口径前置走通——在停闸的同时把「拿到数据后立刻要定的四个口径」（窗口、切点、合并、退款）固定为提问清单，避免数据到位后二次停摆；分层骨架与运营动作建议为可复用成品。

**停在闸门 / 降级部分**：三个执行步骤中步骤 1 完成于停闸判定，步骤 2 未执行，步骤 3 仅交付骨架。根因是**材料体系无客户级消费记录**：`05` §三最细只到「周」，而 RFM 需要「单×客户」粒度。这是 OPC 材料设计边界，不是执行失败；同组 `wf-ecom-repurchase-remind` 因同一根因停闸，两单元共享同一份订单导出需求（用户补一次数据可同时解锁两者）。

**触发方式偏差**：工作流触发为「定时（每周）」，需要订单导出管道；当前连接器全部 unbound，定时路径在当前环境不存在，本次以人工触发验证。

**发现（技能缺陷，按当前仓库版本）**：
1. `rfm-segmentation` 输入契约只写「消费记录」一个词，未列最小字段集（客户标识/日期/金额）与口径确认项（窗口/切点/退款）——本次的口径清单全部由执行者自拟，不同执行者产出会不一致。
2. 工作流「业务收益：月省数据分析 8h≈¥240」无输入可回指，宣传性表述。
3. 工作流步骤 1「订单导出」名不副实：执行者无导出工具与连接器，实际动作是「向用户索要导出文件」——步骤命名暗示了不存在的自动化能力。
4. 与 `fan-segment-tag`（粉丝互动分层）存在人群重叠（都产出「分层名单」），但两 SKILL 未互相声明数据边界（互动数据 vs 消费数据），复用同一客户池时可能产出两套冲突名单——建议在依赖关系里写明分工。
